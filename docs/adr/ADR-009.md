# ADR-009: Finding detail shows the collected configuration at the evidence locator

Status: Accepted (0.8.2, pilot feedback).

## Context
The evidence explorer serves a normalized, redacted observation and deliberately hides
policy documents, conditions, e-mail addresses, tags and descriptions. Pilot analysts could
not answer "which configuration caused this finding?" without opening collector files: a
trust-policy finding is about the policy's missing Condition, a GCP IAM finding is about
the bound member and role.

## Decision
- A finding's detail view (`findings/detail.py`, `finding-detail-1.0.0`) shows, for each of
  the finding's own evidence references, the stored raw JSON at that reference's locator,
  read from the integrity-checked workspace copy, with the collector operation, original
  file, JSON path, collection time, coverage, collection errors and SHA-256 result.
- Values under credential keys (the importer's SECRET_KEYS plus key names containing
  secret, password, private key, token, credential, API key or key string) and values that
  look like keys or private-key material are replaced with `***MASKED***`. Policy documents,
  members and roles stay visible because they are the evidence. Snippets are bounded.
- Field-level actual versus expected values come only from fields found in that snippet.
  Expected values, weakness category, principle, remediation and read-only verification
  commands come from a versioned per-rule table and are labelled as analysis or guidance.
  Commands are display text with placeholders and are never executed.
- The evidence explorer's redaction is unchanged.

## Consequences
Analysts see the exact configuration responsible for a finding, locally and offline.
Customer identifiers such as member e-mail addresses appear in the finding view and in
copied technical findings, so outputs remain customer material. Unresolvable locators or
missing files are reported, never filled with example data.
